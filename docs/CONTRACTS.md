# Runtime contracts

This document specifies implemented behavior and test expectations. TypeScript ports are in `src/contracts.ts`.

- Authenticate the exact configured owner handle and enrolled direct chat before persisting message content. Reject groups, outbound echoes, missing metadata, and unrelated chats.
- Enrollment fixes the transport/account/chat and a starting cursor. Never implicitly enroll, replay old commands on first launch, or reuse a cursor with another Messages database identity. Advance a page cursor only in the transaction that saves the accepted messages and their effects.
- An incoming GUID is processed once. Reminder creation, task capture, job creation, and acknowledgement intent are committed together. Foreign text and credentials do not enter logs.
- Explicit complete/snooze commands resolve an ID or a single active reminder; ambiguity produces a question. Snooze changes notification time, not the original deadline. Completion invalidates pending reminder messages.
- Supported reminder grammar consumes the entire input. Unknown/compound instructions are retained as jobs, never silently truncated into a simpler action. Resolve dates relative to the message timestamp in the configured IANA timezone; reject nonexistent/ambiguous local times and unclear meridiems.
- Provider timestamps must include a UTC offset and a valid calendar date. Relative calendar-day reminders also reject DST gaps/folds. Clarification replies show a complete replacement command because conversational slot-filling is not implemented yet.
- `pause` suppresses discretionary nudges; `pause all` holds requested reminders too. Replies and control commands still work. `resume` permits due reminders after quiet hours. There are no discretionary nudges in the initial implementation.
- Reminder delivery is at most one automatic send attempt unless the transport proves dispatch did not begin. A timeout, lost response, missing send GUID, or crash during send becomes uncertain. Never automatically resend an uncertain item. An operator may reconcile it against Messages.
- A single process owns the live service. Use a per-data-directory lock; do not silently steal a stale lock. SQLite transactions protect ingestion and state transitions. Restart recovery marks interrupted sends uncertain.
- Jev only records advice for queued work. Timeout, invalid output, or low confidence does not execute an action or lose the job. Commands bypass Jev. Codex capability inspection starts no model turn and claims no computer-use compatibility.
- The local reminder ledger is not an iCloud sync implementation. Replies say "Saved locally"; a native helper is a separate pending integration.
- Live commands require the configured macOS username and explicit owner/chat configuration. The demo uses synthetic messages, an isolated temporary database, a fake clock, and an in-memory transport. It sends no messages and calls no models.
- Enrollment scans the configured chat to its physical cursor without executing or retaining past messages, and requires at least one inbound owner message with complete direct-chat metadata. It checks the database identity before and after the scan. A bounded catch-up must finish before scheduled sends begin.
- `databaseIdentity(config, path)` binds enrollment to the account, owner/chat, canonical database path, device, inode, and birth time. `assertIdentity` halts on a mismatch. The RPC child uses that exact database path.
- `acquireLock(dataDir)` returns an idempotent release function. It refuses existing locks (including stale locks) and symlink data directories. Only its own lock can be released.
- `enroll(store, transport, identity)` records a fresh watermark after a complete scan. `catchUp(store, coordinator, transport, checkIdentity, maxPages)` checks identity around each page, commits only valid pages, and returns whether the scan reached the tail. Neither operation sends messages.
- CLI commands: `demo` is isolated; `doctor`, `enroll`, `status`, `probe-codex`, and `run` require `--config` and the assistant profile. `doctor` reads readiness only. `run` requires prior enrollment and a data-directory lock. No command silently installs a background service or grants permissions.
- `runService` polls independently of sends and advisory routing. It ingests controls while an earlier send is in flight, checks identity before every dispatch, and stops on transport/read/identity failure. Shutdown closes the transport, waits for pending work, and leaves ambiguous sends uncertain. Its optional injected wait function is for deterministic lifecycle tests.
- Snooze offsets use the command's message timestamp, including during catch-up; delayed ingestion never extends the requested snooze. The original deadline remains unchanged.
- Explicit compound markers (including semicolons, newlines, and "and also") apply to note/remember captures as well as reminders. Such requests remain intact as queued jobs.
- A failed identity check before dispatch leaves the claimed message retryable and prevents all subsequent dispatches in that service run, even if a later identity check would succeed. Only attempts that reached the transport can become uncertain.
- `runService` halts on an uncertain send outcome or a thrown send error, retaining that item as uncertain and later items as pending for operator-reviewed restart. An authoritative `not_started` outcome remains eligible for backoff and retry.
- `Store.claimUnroutedJob()` atomically marks the oldest queued, unattempted job before returning it. Advisory attempts are not repeated after restart. `Coordinator.routeJobs(router, shouldContinue?)` rechecks cancellation and the optional lifecycle gate before each claim; a cancelled job or stopped service cannot start another advisory call. In-flight advice may finish, but cannot restore a cancelled job.
