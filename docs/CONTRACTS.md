# Runtime contracts

This document specifies implemented behavior and test expectations. TypeScript ports are in `src/contracts.ts`.

## Engine and contacts

- The engine owns transport, enrollment, per-conversation cursors, identity checks, inbox deduplication, the outbox, contacts and permissions, durable timers, and tasks. Plugins supply capabilities. The engine is transport-agnostic; `MessageTransport.readAfter` and `send` take the target conversation.
- Configuration lists approved `contacts`. Each has a lowercase id, name, exact handles, one direct iMessage conversation, a role (`owner` or `member`), and a plugin allowlist. Ids, handles, and conversations are unique across contacts; exactly one contact is the owner. Groups stay rejected. The former single `owner` entry is refused.
- Authenticate the sending contact's exact handle and its own enrolled direct conversation before persisting message content. Reject groups, outbound echoes, missing metadata, unrelated chats, and an approved handle writing in another contact's conversation.
- Every message, task, timer, plugin document, and outgoing reply is scoped to its contact. Replies go only to that contact's conversation. `pause`, `resume`, `status`, and `cancel` affect only the sender. `ImessageTransport` reads and sends only in configured conversations.
- Enrollment is a CLI-only operator step, one conversation at a time (`enroll --contact <id>`). A message can never enroll its sender. Enrollment scans that conversation to its physical cursor without executing or retaining past messages, requires at least one inbound message from that contact with complete direct-chat metadata, and checks the database identity before and after each page. Never implicitly enroll or replay old commands. Re-enrolling an enrolled contact is refused.
- `databaseIdentity(assistantUser, path)` (version 2) binds the Messages database to the assistant account, canonical path, device, inode, and birth time. The first enrollment records it; later enrollments and `run` must match it. `assertIdentity` halts on a mismatch. Contact configuration is not part of the identity: each conversation has its own enrollment record, and a configured conversation that differs from its enrollment halts processing until an operator reviews it. Configured but unenrolled contacts are inactive and their conversations are not read.
- An incoming GUID is processed once. The message, its dispatch effects, the acknowledgement intent, and the conversation cursor are committed in one transaction. Advance a cursor only in the transaction that saves that page's accepted messages. Foreign text and credentials do not enter logs.
- A state database from before contacts (schema 1) is refused with instructions to move it aside and enroll again.

## Dispatch

- Order: engine commands, then plugin grammars, then an answer to the runtime's open question, then Jev, then validation, then execution in a plugin or the runtime. With conversational replies, Jev and the later steps run while the message waits in order; see [Conversational replies](#conversational-replies).
- Engine commands are deterministic and need no model: `help`, `status` (also `what's happening?`), `pause`, `pause all`, `resume`, `cancel #n` (also `cancel job #n`), `stop`, `approve A<code>`, `deny A<code>`, `continue #n`, and `#n <text>`. `continue` may leave off the number when exactly one job is paused; `approve` and `deny` without a code only list the pending code.
- Explicit compound markers (semicolons, newlines, "and also", "and then", and similar) bypass every plugin grammar, so a second instruction is never truncated. Such requests are retained whole as tasks. Whitespace, including newlines, at the start or end of a message is not a marker, for grammars or for Jev routes.
- Each permitted plugin gets one whole-message `match` in registry order; the first match wins. A match may return a command, one clarification question, or nothing. Commands are validated against the plugin's declared schema (known kind, exact fields, types, and bounds) before `handle` runs.
- Without conversational replies, unmatched text becomes a durable task with its full text, numbered per contact, and gets one acknowledgement. Without runtime access it says the job is queued. Tasks can be cancelled with `cancel #n` until they finish.
- When exactly one of the contact's jobs is waiting on a delivered runtime question, an unmatched message written after that question's send began answers it; earlier messages become new jobs. In conversational mode, a conversational question, any other reply of Nori's that asks something (for example a grammar handler's "Which reminder?", or a phrased chat reply), as delivered, or a reminder message Nori sent that contact after the runtime question takes precedence while it is open (until a message they sent after its delivery is handled in any way; one still held, for example by `pause all`, stays open), so the reply goes to understanding instead, which can still send it to the job (see `continue` below). With several waiting, Nori asks once which job it is for and creates no task.
- A thrown plugin error, invalid command, or returned promise from a synchronous hook fails that dispatch only: its savepoint rolls back, the request is retained as a task with a failure label that never contains message text, the contact gets a short retained-task message, and the task is not sent to Jev.

## Plugins

- An `ActionPlugin` declares a manifest (id, version, state version, capabilities, default roles, routing criteria, help examples), a command schema, a migration hook, a grammar, an optional `interpret` step, `handle`, and optional `onTimer` and `summary` hooks. Plugin ids are lowercase; `runtime`, `continue`, `clarify`, `chat`, `status`, `pause`, `resume`, and `cancel` are reserved. An optional `label` completes "Do you want me to …?" questions.
- A plugin runs for a contact only when the contact's allowlist names it and its manifest permits the contact's role. Unknown plugins in an allowlist or Jev route, duplicate ids, and invalid manifests are refused at startup. Manifests are snapshotted at registration so a plugin cannot widen its own permissions.
- `handle`, `onTimer`, `summary`, and `match` are synchronous. The first three run inside the engine's transaction; a returned promise is refused and rolled back. `interpret` may be asynchronous and receives a read-only context; it returns a command, a clarification, or null when it cannot read the message. `describe` is synchronous and read-only; it returns the code-written account of a validated command: a description the contact can confirm, and the instants the command sets. A context is valid only during its dispatch. `MessageContext.conversational` tells plugins whether replies may invite plain answers instead of command syntax.
- `PluginContext` exposes the frozen contact, reference time, timezone, `reply`, `schedule`, `cancelTimer`, `state`, `delegate`, and `extract`, which is set only during a conversational `interpret`. Plugins never see the store or the transport. `state` and timers require the `storage` and `schedule` capabilities. State is JSON documents namespaced by plugin and contact, with per-contact sequences. `migrate(db, from)` runs once per state-version increase, in a transaction, before the plugin handles anything; newer stored state is refused.
- Timers are durable and upserted by key. Each due timer fires at most once. Re-scheduling or cancelling a key bumps its revision, which cancels unsent messages from earlier fires. Timers of inactive contacts or unpermitted plugins wait. A thrown `onTimer` marks the timer failed without refiring it.
- `delegate(text, hint)` creates a durable task for a runtime that preserves the full text and does not go to Jev.

## Reminders plugin

- Reminders is the first in-process plugin. It owns the reminder grammar, reminder state, and reminder timers. Replies say "Saved locally"; the local ledger is not an iCloud sync implementation.
- The grammar consumes the entire input. Resolve dates relative to the message timestamp in the configured IANA timezone; reject nonexistent/ambiguous local times and unclear meridiems. Relative calendar-day reminders also reject DST gaps/folds. Without conversational replies, clarifications show a complete replacement command.
- `done` and `snooze` resolve an id or a single active reminder; ambiguity produces a question. Snooze offsets use the command's message timestamp, including during catch-up, and change the notification time, not the original deadline. Completion cancels pending reminder messages. `list` shows the contact's active reminders. `summary` gives each reminder's next time, and its original deadline when snoozed, so `status` and the models' view of what the contact is tracking include when things are due.
- `interpret` accepts polite phrasing around the same grammar (for example "Can you remind me to call mom in 2 hours?"). Without `extract` it otherwise asks one focused question. With `extract`, the responder fills a strict schema (action, title, reminder number, time parts, snooze minutes, and what is missing) from the message, the recent conversation, and the contact's numbered active reminders. Models name time parts and code resolves them: times must be in the future, within 366 days, and not in a DST gap or repeat (a weekday whose time has already passed today means next week, and only that target date is checked); vague times get stated defaults; reminder numbers must exist; snoozes stay within one week. Missing details become one question (which reminder, what about, or when). An unusable answer returns null. With `extract`, commands always name their reminder: a grammar match that leaves the reminder implicit (`done`, `snooze 20m`) is bound to the single active reminder, or becomes the which-reminder question when there is not exactly one. Without it, such a command is returned as is, and `handle` answers an ambiguous one with the complete commands to send.
- `describe` states the change in plain words (shortening a long title) with its local day, date, and time, for example `remind you about “call mom” tomorrow (Tue, Sep 29) at 9:00 AM`; the date keeps it unambiguous when it is read on a later day. In conversational mode, reminder messages invite a plain answer ("Tell me when it's done, or ask me to snooze it.") instead of command syntax.

## Delivery

- `pause` suppresses discretionary nudges; `pause all` holds that contact's timer messages too. Replies and control commands still work. Quiet hours hold timer messages. `resume` permits due reminders after quiet hours. There are no discretionary nudges yet.
- Delivery is at most one automatic send attempt unless the transport proves dispatch did not begin. A timeout, lost response, missing send GUID, or crash during send becomes uncertain. Never automatically resend an uncertain item. An operator may reconcile it against Messages. Messages for a contact removed from configuration are held, not sent.
- A single process owns the live service. Use a per-data-directory lock; do not silently steal a stale lock. Restart recovery marks interrupted sends uncertain.
- `acquireLock(dataDir)` returns an idempotent release function. It refuses existing locks (including stale locks) and symlink data directories. Only its own lock can be released.
- `catchUp(store, engine, transport, checkIdentity, maxPages)` reads every enrolled conversation, checks identity around each page, commits only valid pages, and returns true only when every conversation reached its tail. A bounded catch-up must finish before timers fire or sends begin.
- `runService` polls independently of sends and routing. It ingests controls while an earlier send is in flight, checks identity before every dispatch, and stops on transport/read/identity/enrollment failure. A failed identity check before dispatch leaves the claimed message retryable and prevents all later dispatches in that run. It halts on an uncertain send outcome or a thrown send error, retaining that item as uncertain and later items as pending. An authoritative `not_started` outcome remains eligible for backoff and retry. Shutdown closes the transport, waits for pending work, and leaves ambiguous sends uncertain. Its optional injected wait function is for deterministic lifecycle tests.

## Jev routing

- Only unmatched tasks go to Jev; engine commands and grammar matches never do. The catalog is generated per contact from permitted plugins with an `interpret` step, plus `runtime` (owner only), `continue`, and `clarify`. Its version is a digest of option ids and criteria. Conversational catalogs differ; see below.
- One request asks a Choice over the catalog and a Noul for whether the request contains more than one action. The state sent is the request text and timezone. The decision records model, catalog version, route, confidence, probabilities, and the multiple-action answer. Malformed answers, choices outside the catalog, bad distributions, HTTP failures, and timeouts abstain.
- Routing is shadow-only by default: the decision is recorded and the task stays queued, or goes to the runtime for contacts who may use one. A plugin's route acts only when `jev.routes` names it with a threshold, the confidence meets that threshold, the answer is a single action, the text has no compound marker, and the contact is still permitted to use the plugin. Then `interpret` runs, its result is validated, and `handle` executes; the task completes. A clarification is sent once; it asks for a complete new request, so the task is closed as failed with the question as its outcome. Failures leave the task queued with a failure label. Runtime, continue, and clarify routes are recorded only.
- `Store.claimUnroutedTask()` atomically marks the oldest routable task attempted and counts it against `jev.dailyLimit` for the configured local day, which every Jev request shares; past the limit, tasks wait unrouted. Attempts are not repeated after restart. A contact's tasks are not claimed for routing while one of that contact's messages is pending, and a plugin route decided meanwhile does not act: the task returns to routing once the messages are handled, so a cancellation already sent takes effect first. `Engine.routeTasks(router, shouldContinue?)` rechecks cancellation and the lifecycle gate before each claim; a cancelled task or stopped service cannot start another routing call. Late advice cannot restore or execute a cancelled task.
- Labeled examples in `test/fixtures/routing.json` pin which requests bypass Jev and what an enabled route does with each label.

## Runtime (Codex)

- The runtime is enabled by `runtime` in configuration and is owner-only by default. Every unmatched owner request that no plugin route acts on goes to it: after Jev chooses a non-plugin option, after Jev abstains or fails, past the daily Jev budget, or when Jev is disabled. Tasks a plugin creates with `delegate`, and any queued task routing already passed over, go to it without Jev. Retained plugin failures stay queued. Members' jobs stay queued.
- Task states: queued, routed (waiting to start), running, waiting for the contact (a question, an approval, a budget limit, or an interruption), completed, failed, cancelled. Up to `runtime.maxJobs` turns (1–8, default 1) run at once across all contacts, and a task has at most one turn at a time. Whenever a slot is free, the oldest routed task the daily limits allow starts. Intake, timers, sends, and engine commands stay responsive while turns run. `Engine.runTasks` fills the free slots and resolves when the turns it started end; `runService` calls it on every poll, so a slot freed by one job is refilled without waiting for the others. If a turn's result cannot be recorded, `runTasks` rejects at once, so the service stops before another job starts, and `Engine.idle()` lets shutdown wait for the turns still running.
- Messaging: one acknowledgement at intake, then only a question, an approval request, a limit or interruption notice, or the result. Tool logs and progress are never forwarded. A result is `Job #n is done. …` only when the runtime reports `completed` with at least one evidence item; the engine checks this itself, and a completion without evidence fails the job. Outcomes and evidence are stored on the task.
- Follow-ups (`#n <text>`, or an answer to the one open question) resume the same thread, each marked with its send time. A follow-up that arrived during a turn that failed starts another turn. Input sent before the first turn, including while the job is still being routed, joins the request. Input sent during a turn starts another turn when it ends, unless the turn ends with a question: a question always waits for the contact, and the queued input goes with the answer.
- Approvals: a runtime approval request or a call to a high-impact tool creates a durable approval bound to the contact, task, operation, parameters, and expiry, and sends one question showing everything it would grant (the command and the files to be changed, which must be known or the request is refused; any extra access, including permission entries, which must be describable or the request is refused; working directory, network hosts, extra file or network access, files to be changed, or the tool's full arguments). A request too long to show in full is refused without asking. A job has at most one pending approval; later requests wait until it is decided. Different jobs' approvals are independent. Each prompt carries the approval's own code, and only that contact's `approve A<code>` or `deny A<code>` resolves it, so a reply can never authorize a different operation. Prompts that can no longer be answered are withdrawn if still unsent. An overdue approval is refused even before a tick expires it. Denial, expiry (`approvalMinutes`), cancellation, a budget interruption, and the end of the turn all refuse it. After a budget interruption the turn gets no further approvals or tools. Approval waits do not count against the time budget. If an approval request cannot be recorded, the request fails and the job's running time keeps counting.
- Tools: the runtime sees only tools exported by plugins the task's contact may use, named `<pluginId>_<kind>`. Each call re-checks permission, validates arguments against the command schema, runs `handle` in a transaction with its replies returned as the tool result instead of sent, and is recorded once per call id; a repeated call id returns the recorded result, and a concurrent call with the same id shares the first call's approval and result. A tool call's reference time is when it runs, so a snooze's minutes count from then; the runtime is told when each request was sent and chooses arguments accordingly.
- Budgets: per task, running minutes, turns, tool calls (plugin tool calls and the runtime's own commands, file changes, and searches), and tokens; per local day, started tasks and tokens. Budget and approval-expiry checks run on every poll, even while a send is in flight. Every budget is checked before each turn starts. A running turn is stopped as soon as its tokens reach the budget, the same boundary checked before a turn starts. The runtime's own actions cannot be refused before they start, so once they reach the tool-call budget the turn is interrupted as soon as the last one finishes, and at once if another starts. Reaching a task budget interrupts the turn (re-sent on each poll until the turn ends; the stop holds even if the turn ends with a question) and leaves the task waiting with a next-decision message; `continue #n` grants one more allowance. Reaching a daily budget holds routed tasks until the next day. Daily budgets are checked when a turn starts, so turns already running may carry the day past a limit.
- Cancellation: `cancel #n` or `stop` interrupts the active turn, refuses its approvals, and withdraws the job's unsent messages; a cancel that arrives before the turn has started keeps it from starting, and an interrupt that cannot be confirmed closes the runtime connection. Queued input stays on the task until the runtime accepts the turn. All turns share one app-server connection, so closing it for any reason ends every active turn, and each of those tasks waits as interrupted. If Codex does not confirm a turn start, Nori closes the connection, which stops any turn it may have begun; the thread id is saved as soon as the thread exists, so `continue #n` resumes it rather than starting over. It does not reverse effects already made. Closing the connection pauses the app-server and every process it started, including commands Codex runs in their own sessions and processes a command left behind after it exited: any process carrying the connection's random environment tag (`NORI_PROCESS_TAG`), and every member of a process group, other than Nori's own, that a process already found belongs to. Then it kills them all, looking for new processes in every listing while it does, and counts them stopped only once a listing shows none of them running and nothing new; a tagged process seen in the environment listing but missing from the process listing, which are taken separately, counts as still running, and so does a process already found that later shows a different or missing start time while tagged; the turn ends, and a new connection or job starts, only after they have exited. Service shutdown uses `Runtime.shutdown`, which also refuses every later start or resume, including one still waiting for an earlier close to finish, so no connection opens after the service stops; it waits for this before releasing the lock. If Nori cannot confirm they stopped (the process list is unavailable, or something survives), the runtime halts: its turns end, nothing more starts, and the service stops with the reason and keeps its lock until the operator has checked. If the app-server exits on its own, the connection closes at once, even while something it started still holds its output, and closing still finds what it left behind by the tag and by process group, as above. A process that is neither tagged nor in a found process's group cannot be traced: macOS hides the environment of its own system binaries, so for example a background `sleep` whose launching shell has exited, alone in its group, or anything started through launchd. Running Codex under a separate macOS account would close this gap.
- Recovery: a lost connection or a restart leaves the task waiting as interrupted, with pending approvals expired. Nori never resubmits a turn automatically. `continue #n` resumes the thread and first tells the runtime to check what was already done.
- The Codex adapter speaks the app-server protocol over stdio with the experimental API: one persisted thread per task in a private `task-<id>` directory under `workspaceDir`, plugin tools as dynamic tools, and a structured final message (`outcome`, `message`, `evidence`). Every turn pins `on-request` approvals reviewed by the user (never a model) and a `workspace-write` sandbox with no extra writable roots and no network, whatever the local Codex configuration says. The child process gets a minimal environment without Nori's secrets, and Nori never passes it its database, transport, or credentials. It runs with Nori's own Codex home (`<dataDir>/codex` as `CODEX_HOME`), so the account's Codex login, configuration, execution rules, and trusted projects do not apply. Codex execution rules can run a matching command outside the sandbox without asking, whatever the approval policy, so before every turn Nori reads the active configuration layers for the task directory from Codex (`config/read`). If any active layer has a `rules` folder with entries, or a layer's folder cannot be found or read, the turn does not start and the job fails with the reason. Layers Codex reports as disabled, such as untrusted projects, are skipped. The sandbox does not restrict reads, so commands can read files the assistant account can read, including Nori's state database. Unrecognized server requests are refused. Computer use is unverified, so GUI tasks are out of scope.

## Conversational replies

- Enabled by `responder`, which requires `jev`. Without it, behavior is as above and no message waits for understanding. `Engine` accepts a `ConversationPort` only when both are configured.
- Engine commands and plugin grammar matches still apply at once, model-free. Every other message is stored at stage `pending` without a reply, and so is every later message from the same contact while one of theirs is pending, in any mode, except the controls that stop activity: `stop`, `cancel #n`, and `deny A<code>` apply at once, so a running job never keeps acting while an earlier message is understood. Their replies may arrive before the earlier message's reply. In conversational mode a grammar clarification also goes to understanding instead of being sent. `Engine.processPending(shouldContinue, signal)` handles each contact's pending messages strictly in row order; contacts proceed independently. It first dispatches the message exactly as on arrival (commands, grammars, an answer to the runtime's open question); only a still-unmatched message reaches the models. The service runs it whether or not a responder is configured.
- `Store.claimPendingMessage(contactId)` durably counts an attempt before any model call. A message gets at most two model attempts across restarts. After that, and after a failed or unusable understanding, a null `interpret`, or an exhausted budget, the model-free path keeps the message as a job with the usual acknowledgement. An abort during a model call leaves the message pending. The service aborts model calls on shutdown and on any failure that stops it.
- Models never produce actions. Jev understands the message with a conversational catalog: the contact's permitted plugins with both `interpret` and `describe`, then `runtime`, `continue`, `clarify`, `chat`, `status`, `pause`, `resume`, and `cancel`, with the Choice's confidence and probabilities (which must name exactly the catalog's options and sum to one), a multiple-action Noul, and an outbound Noul. Code gates the answer (`gate`):
  - explicit compound markers (as in dispatch), outbound or multiple actions (at least 0.5), confidence below `thresholds.clarify`, `runtime`, `continue` below `thresholds.act`, or a plugin that `jev.routes` does not enable: the message is kept as a job, with the decision recorded so it is not routed again;
  - `clarify`: one question asking the contact to say it another way;
  - `chat` and `status`: a reply that changes nothing;
  - confidence below the option's acting threshold (`jev.routes[id]` for a plugin, `thresholds.act` for `pause`, `resume`, and `cancel`): one question offering the two likeliest options;
  - otherwise the change is prepared.
- A plugin change runs `interpret` with `extract`, validates the command against the plugin's schema, and asks `describe` for its account. An engine change uses a fixed account: `pause` holds all reminder messages, `resume` releases them, `cancel` targets the contact's only open job or one the responder picks from the numbered list, which must exist, and `continue` sends the message to the one job waiting on a question delivered before the message was sent (with none or several, the message is kept as a job). Every change needs Jev to rate its code-written description at `thresholds.verify` or above; otherwise, or if the check is unavailable, the contact is asked `Did you mean: … ? Say yes, or tell me what to change.` and nothing changes. A later "yes" is understood from the conversation like any message and checked again. At commit, the plugin's account is taken again; if it changed meanwhile (for example, another change touched the same reminder), nothing changes and the contact is asked to say it again. Plugin errors become retained jobs with failure labels, as in dispatch.
- The effect and a template reply commit in one transaction with the message's stage. A plugin's replies are captured and committed as one reply. Questions, including confirmations, and answers such as `status` are sent exactly as code wrote them, so a contact's "yes" confirms what code will do and stated deadlines are the stored ones. Only results of committed changes and chat replies are phrased; they commit as `drafting`. A model-phrased reply replaces the template only if code finds every required mention (the template's `#n` numbers, and for pause `resume`), every instant's local clock time and explicit calendar date (and no other weekday or date; a stated year must be the instant's, and the year is required when it differs from the current one), no relative day or duration words (`today`, `tonight`, `tomorrow`, `this morning`, `next week`, `in 2 hours`, …), since a reply may be read later than it was written; ISO dates, `noon`, and `midnight` count as dates and times, no `#n` beyond the template's (or, for chat, beyond the contact's tracked items and jobs), no clock time, calendar date, or weekday other than those of the committed instants (so none in chat), and at most 700 characters. Every phrased reply must also pass the `claimsAction` screen against the code-written account: the template for a committed change, nothing for chat. Otherwise the template is sent.
- A `drafting` reply holds the same contact's later replies. `recoverInFlight` releases drafting replies with their committed template text. A contact's timer messages are not sent, and their jobs do not start or resume, while any of that contact's messages is pending, so a completion, snooze, or instruction already sent takes effect first. The service starts a drain on every poll; contacts already draining are skipped, so one contact's slow model call never holds another contact's messages.
- Models see at most eight delivered turns with the contact from the last six hours, the status lines of the contact's permitted plugins, and up to five of their open jobs. Turns are the contact's handled messages plus Nori messages whose send began (sending, sent, or uncertain), timed by when they were sent, so reminders held by quiet hours or a pause stay in context and a question being sent is visible to its answer. Turns sent after the message itself are left out, since the contact had not seen them. Each turn is shown to the models with its local send time, and extraction reads relative words from the message they appear in, naming an explicit date when that is not the latest message. Plugins add their own data to extraction requests.
- Every model request reserves one call against its provider's daily limit for the local day in SQLite before leaving the process: `jev.dailyLimit` for all Jev requests and `responder.dailyLimit` for the responder. A provider without a configured limit is refused. `status` says when a limit is reached. `chat` meters against its own console store, and each `eval` run has its own in-memory ceiling of `jev.dailyLimit`; neither counts against the live service.
- API keys come from the environment or, on macOS, the login Keychain (`ai.nori.typesafe`, `ai.nori.openrouter`). They never come from config, plists, or arguments, they are never logged, and they are removed from the environment of every child process.
- OpenRouter requests use strict JSON Schema output, `data_collection: "deny"`, `require_parameters: true`, and reasoning off. A Codex responder uses Nori's Codex home and a separate app-server with shell, apps, plugins, browser, computer use, image generation and viewing, skills search, sleep, sub-agents, memories, hooks, web search, and MCP servers disabled; each request is a new ephemeral, read-only thread with approvals `never`, interrupted on timeout or abort, including a turn whose start is only confirmed afterwards (by notification or a late response) or whose start response is malformed. If a start fails without ever naming its turn, or an interrupt fails, that responder connection is closed, which stops anything it started; the next request opens a new one. Because a lower Codex configuration layer (for example `/etc/codex/config.toml`) can add MCP servers that the `mcp_servers={}` override does not remove, the responder reads Codex's effective configuration for its working directory before using a connection, and refuses it (every request returns null and the connection is closed) unless every feature it disables (including image viewing, skills search, and sleep) reports off, web search is disabled, and no enabled MCP server remains.
- Store schema version 3 adds the inbox stage and attempts and the daily usage table. Version 2 databases migrate in place; existing messages are treated as handled, and each day's routing calls carry over into the usage table so the Jev limit is not reset.

## CLI and demo

- Live commands require the configured macOS username and explicit contact configuration. `demo` is isolated: synthetic messages, a temporary database, a fake clock, and an in-memory transport; it sends no messages and calls no models.
- `chat` and `eval` are development commands and run on any OS. `chat` runs the real service loop with a console transport, one synthetic owner contact, `console.sqlite`, and the data-directory lock; it reads only `timezone`, `quietHours`, `jev`, and `responder` from its config file (a Codex responder without `codexPath` takes the file's `runtime.codexPath`). `eval` sends labelled cases to TypeSafe only and reports how the gate would treat each. On end of input, `chat` stops only once the service is idle: everything typed has been read, understood, routed, and answered (`runService`'s `until` option). A failure recorded meanwhile, such as an uncertain send, still stops it with an error.
- `doctor`, `enroll --contact <id>`, `status`, `probe-codex`, and `run` require `--config` and the assistant profile. `doctor` reads readiness only. `run` requires at least one enrolled contact, a data-directory lock, and an executable `runtime.codexPath` when a runtime is configured. No command silently installs a background service or grants permissions.
- `probe-codex` starts no model turn and claims no computer-use compatibility.
