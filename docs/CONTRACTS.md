# Runtime contracts

This document specifies implemented behavior and test expectations. TypeScript ports are in `src/contracts.ts`.

## Engine and contacts

- The engine owns transport, enrollment, per-conversation cursors, identity checks, inbox deduplication, the outbox, contacts and permissions, durable timers, and tasks. Plugins supply capabilities. The engine is transport-agnostic; `MessageTransport.readAfter` and `send` take the target conversation.
- Configuration lists approved `contacts`. Each has a lowercase id, name, exact handles, one direct iMessage conversation, a role (`owner` or `member`), and a plugin allowlist. Ids, handles, and conversations are unique across contacts; exactly one contact is the owner. Groups stay rejected. The former single `owner` entry is refused.
- Authenticate the sending contact's exact handle and its own enrolled direct conversation before persisting message content. Reject groups, outbound echoes, missing metadata, unrelated chats, and an approved handle writing in another contact's conversation.
- Every message, task, timer, plugin document, and outgoing reply is scoped to its contact. Replies go only to that contact's conversation. `pause`, `resume`, `status`, and `cancel` affect only the sender. `ImessageTransport` reads and sends only in configured conversations.
- Enrollment is a CLI-only operator step, one conversation at a time (`enroll --contact <id>`). A message can never enroll its sender. Enrollment scans that conversation to its physical cursor without executing or retaining past messages, requires at least one inbound message from that contact with complete direct-chat metadata, and checks the database identity before and after each page. Never implicitly enroll or replay old commands. Re-enrolling an enrolled contact is refused.
- `databaseIdentity(assistantUser, path)` (version 2) binds the Messages database to the assistant account, canonical path, device, inode, and birth time. The first enrollment records it; later enrollments and `run` must match it. `assertIdentity` halts on a mismatch. Contact configuration is not part of the identity: each conversation has its own enrollment record, and a configured conversation that differs from its enrollment halts processing until an operator reviews it. Configured but unenrolled contacts are inactive and their conversations are not read.
- An incoming GUID is processed once. The message, its dispatch effects, the acknowledgement intent, and the conversation cursor are committed in one transaction. Advance a cursor only in the transaction that saves that page's accepted messages. Foreign text and credentials do not enter logs.
- A state database from before contacts (schema 1) is refused with instructions to move it aside and enroll again.

## Dispatch

- Order: engine commands, then plugin grammars, then an answer to the runtime's open question, then Jev, then validation, then execution in a plugin or the runtime.
- Engine commands are deterministic and need no model: `help`, `status` (also `what's happening?`), `pause`, `pause all`, `resume`, `cancel #n` (also `cancel job #n`), `stop`, `approve #n`, `deny #n`, `continue #n`, and `#n <text>`. The number may be left off `approve`, `deny`, and `continue` when exactly one job is waiting on that decision.
- Explicit compound markers (semicolons, newlines, "and also", "and then", and similar) bypass every plugin grammar, so a second instruction is never truncated. Such requests are retained whole as tasks.
- Each permitted plugin gets one whole-message `match` in registry order; the first match wins. A match may return a command, one clarification question, or nothing. Commands are validated against the plugin's declared schema (known kind, exact fields, types, and bounds) before `handle` runs.
- Unmatched text becomes a durable task with its full text, numbered per contact, and gets one acknowledgement. Without runtime access it says the job is queued. Tasks can be cancelled with `cancel #n` until they finish.
- When exactly one of the contact's jobs is waiting on a runtime question, an unmatched message answers it. With several waiting, Nori asks once which job it is for and creates no task.
- A thrown plugin error, invalid command, or returned promise from a synchronous hook fails that dispatch only: its savepoint rolls back, the request is retained as a task with a failure label that never contains message text, the contact gets a short retained-task message, and the task is not sent to Jev.

## Plugins

- An `ActionPlugin` declares a manifest (id, version, state version, capabilities, default roles, routing criteria, help examples), a command schema, a migration hook, a grammar, an optional `interpret` step, `handle`, and optional `onTimer` and `summary` hooks. Plugin ids are lowercase; `runtime`, `continue`, and `clarify` are reserved.
- A plugin runs for a contact only when the contact's allowlist names it and its manifest permits the contact's role. Unknown plugins in an allowlist or Jev route, duplicate ids, and invalid manifests are refused at startup. Manifests are snapshotted at registration so a plugin cannot widen its own permissions.
- `handle`, `onTimer`, `summary`, and `match` are synchronous. The first three run inside the engine's transaction; a returned promise is refused and rolled back. `interpret` may be asynchronous and receives a read-only context. A context is valid only during its dispatch.
- `PluginContext` exposes the frozen contact, reference time, timezone, `reply`, `schedule`, `cancelTimer`, `state`, and `delegate`. Plugins never see the store or the transport. `state` and timers require the `storage` and `schedule` capabilities. State is JSON documents namespaced by plugin and contact, with per-contact sequences. `migrate(db, from)` runs once per state-version increase, in a transaction, before the plugin handles anything; newer stored state is refused.
- Timers are durable and upserted by key. Each due timer fires at most once. Re-scheduling or cancelling a key bumps its revision, which cancels unsent messages from earlier fires. Timers of inactive contacts or unpermitted plugins wait. A thrown `onTimer` marks the timer failed without refiring it.
- `delegate(text, hint)` creates a durable task for a runtime that preserves the full text and does not go to Jev.

## Reminders plugin

- Reminders is the first in-process plugin. It owns the reminder grammar, reminder state, and reminder timers. Replies say "Saved locally"; the local ledger is not an iCloud sync implementation.
- The grammar consumes the entire input. Resolve dates relative to the message timestamp in the configured IANA timezone; reject nonexistent/ambiguous local times and unclear meridiems. Relative calendar-day reminders also reject DST gaps/folds. Clarifications show a complete replacement command because conversational slot-filling is not implemented yet.
- `done` and `snooze` resolve an id or a single active reminder; ambiguity produces a question. Snooze offsets use the command's message timestamp, including during catch-up, and change the notification time, not the original deadline. Completion cancels pending reminder messages. `list` shows the contact's active reminders.
- `interpret` accepts polite phrasing around the same grammar (for example "Can you remind me to call mom in 2 hours?") and otherwise asks one focused question.

## Delivery

- `pause` suppresses discretionary nudges; `pause all` holds that contact's timer messages too. Replies and control commands still work. Quiet hours hold timer messages. `resume` permits due reminders after quiet hours. There are no discretionary nudges yet.
- Delivery is at most one automatic send attempt unless the transport proves dispatch did not begin. A timeout, lost response, missing send GUID, or crash during send becomes uncertain. Never automatically resend an uncertain item. An operator may reconcile it against Messages. Messages for a contact removed from configuration are held, not sent.
- A single process owns the live service. Use a per-data-directory lock; do not silently steal a stale lock. Restart recovery marks interrupted sends uncertain.
- `acquireLock(dataDir)` returns an idempotent release function. It refuses existing locks (including stale locks) and symlink data directories. Only its own lock can be released.
- `catchUp(store, engine, transport, checkIdentity, maxPages)` reads every enrolled conversation, checks identity around each page, commits only valid pages, and returns true only when every conversation reached its tail. A bounded catch-up must finish before timers fire or sends begin.
- `runService` polls independently of sends and routing. It ingests controls while an earlier send is in flight, checks identity before every dispatch, and stops on transport/read/identity/enrollment failure. A failed identity check before dispatch leaves the claimed message retryable and prevents all later dispatches in that run. It halts on an uncertain send outcome or a thrown send error, retaining that item as uncertain and later items as pending. An authoritative `not_started` outcome remains eligible for backoff and retry. Shutdown closes the transport, waits for pending work, and leaves ambiguous sends uncertain. Its optional injected wait function is for deterministic lifecycle tests.

## Jev routing

- Only unmatched tasks go to Jev; engine commands and grammar matches never do. The catalog is generated per contact from permitted plugins with an `interpret` step, plus `runtime` (owner only), `continue`, and `clarify`. Its version is a digest of option ids and criteria.
- One request asks a Choice over the catalog and a Noul for whether the request contains more than one action. The state sent is the request text and timezone. The decision records model, catalog version, route, confidence, probabilities, and the multiple-action answer. Malformed answers, choices outside the catalog, bad distributions, HTTP failures, and timeouts abstain.
- Routing is shadow-only by default: the decision is recorded and the task stays queued, or goes to the runtime for contacts who may use one. A plugin's route acts only when `jev.routes` names it with a threshold, the confidence meets that threshold, the answer is a single action, the text has no compound marker, and the contact is still permitted to use the plugin. Then `interpret` runs, its result is validated, and `handle` executes; the task completes. A clarification is sent once and the task waits for the contact. Failures leave the task queued with a failure label. Runtime, continue, and clarify routes are recorded only.
- `Store.claimUnroutedTask()` atomically marks the oldest routable task attempted and counts it against `jev.dailyLimit` for the configured local day; past the limit, tasks wait unrouted. Attempts are not repeated after restart. `Engine.routeTasks(router, shouldContinue?)` rechecks cancellation and the lifecycle gate before each claim; a cancelled task or stopped service cannot start another routing call. Late advice cannot restore or execute a cancelled task.
- Labeled examples in `test/fixtures/routing.json` pin which requests bypass Jev and what an enabled route does with each label.

## Runtime (Codex)

- The runtime is enabled by `runtime` in configuration and is owner-only by default. Every unmatched owner request that no plugin route acts on goes to it: after Jev chooses a non-plugin option, after Jev abstains or fails, past the daily Jev budget, or when Jev is disabled. Tasks a plugin creates with `delegate`, and any queued task routing already passed over, go to it without Jev. Retained plugin failures stay queued. Members' jobs stay queued.
- Task states: queued, routed (waiting to start), running, waiting for the contact (a question, an approval, a budget limit, or an interruption), completed, failed, cancelled. Turns run one at a time. Intake, timers, sends, and engine commands stay responsive while a turn runs.
- Messaging: one acknowledgement at intake, then only a question, an approval request, a limit or interruption notice, or the result. Tool logs and progress are never forwarded. A result is `Job #n is done. …` only when the runtime reports `completed` with at least one evidence item; the engine checks this itself, and a completion without evidence fails the job. Outcomes and evidence are stored on the task.
- Follow-ups (`#n <text>`, or an answer to the one open question) resume the same thread. Input sent before the first turn joins the request. Input sent during a turn starts another turn when it ends, unless the turn ends with a question: a question always waits for the contact, and the queued input goes with the answer.
- Approvals: a runtime approval request or a call to a high-impact tool creates a durable approval bound to the contact, task, operation, parameters, and expiry, and sends one question showing everything it would grant (the command, working directory, network hosts, extra file or network access, files to be changed, or the tool's full arguments). A request too long to show in full is refused without asking. A job has at most one pending approval; later requests wait until it is decided. Only that contact's `approve #n` or `deny #n` resolves it, and only for approvals that already existed when the reply was sent, so a delayed reply cannot authorize a later operation. An overdue approval is refused even before a tick expires it. Denial, expiry (`approvalMinutes`), cancellation, a budget interruption, and the end of the turn all refuse it. After a budget interruption the turn gets no further approvals or tools. Approval waits do not count against the time budget.
- Tools: the runtime sees only tools exported by plugins the task's contact may use, named `<pluginId>_<kind>`. Each call re-checks permission, validates arguments against the command schema, runs `handle` in a transaction with its replies returned as the tool result instead of sent, and is recorded once per call id; a repeated call id returns the recorded result.
- Budgets: per task, running minutes, turns, tool calls (plugin tool calls and the runtime's own commands, file changes, and searches), and tokens; per local day, started tasks and tokens. Budget and approval-expiry checks run on every poll, even while a send is in flight. Reaching a task budget interrupts the turn (re-sent on each poll until the turn ends) and leaves the task waiting with a next-decision message; `continue #n` grants one more allowance. Reaching a daily budget holds routed tasks until the next day.
- Cancellation: `cancel #n` or `stop` interrupts the active turn and refuses its approvals; a cancel that arrives before the turn has started keeps it from starting. If Codex does not confirm a turn start, Nori closes the connection, which stops any turn it may have begun; the thread id is saved as soon as the thread exists, so `continue #n` resumes it rather than starting over. It does not reverse effects already made.
- Recovery: a lost connection or a restart leaves the task waiting as interrupted, with pending approvals expired. Nori never resubmits a turn automatically. `continue #n` resumes the thread and first tells the runtime to check what was already done.
- The Codex adapter speaks the app-server protocol over stdio with the experimental API: one persisted thread per task in a private `task-<id>` directory under `workspaceDir`, plugin tools as dynamic tools, and a structured final message (`outcome`, `message`, `evidence`). Every turn pins `on-request` approvals reviewed by the user (never a model) and a `workspace-write` sandbox with no extra writable roots and no network, whatever the local Codex configuration says. The child process gets a minimal environment without Nori's secrets, and Nori never passes it its database, transport, or credentials. The sandbox does not restrict reads, so commands can read files the assistant account can read, including Nori's state database. Unrecognized server requests are refused. Computer use is unverified, so GUI tasks are out of scope.

## CLI and demo

- Live commands require the configured macOS username and explicit contact configuration. `demo` is isolated: synthetic messages, a temporary database, a fake clock, and an in-memory transport; it sends no messages and calls no models.
- `doctor`, `enroll --contact <id>`, `status`, `probe-codex`, and `run` require `--config` and the assistant profile. `doctor` reads readiness only. `run` requires at least one enrolled contact, a data-directory lock, and an executable `runtime.codexPath` when a runtime is configured. No command silently installs a background service or grants permissions.
- `probe-codex` starts no model turn and claims no computer-use compatibility.
